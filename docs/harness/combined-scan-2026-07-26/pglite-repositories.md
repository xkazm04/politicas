# PGlite Repositories — Combined Bug-Hunt + UI-Perfectionist Scan
> Total: 5

## 1. `setTieReviewState` audit-then-update is not atomic — concurrent reviews lose data
- **Lens**: Bug
- **Severity**: Critical
- **Category**: race-condition / transaction-safety
- **File**: lib/db/pglite/repositories/review.ts:29-70
- **Scenario**: Two reviewers (or one reviewer double-clicking, or a retpercentagey after a slow network response) call `setTieReviewState` for the *same* `(src, rel, dst)` tie at nearly the same time, one deciding `confirm` and the other `needs-more`. Both requests execute step 1 (`select props from kg_edge ...`) before either executes step 3 (`update kg_edge set props = ...`), because there is no `begin`/`commit` and no row lock (no `select ... for update`) around the read-modify-write.
- **Root cause**: The function reads `props`, computes `nextProps` in JS by spreading the value it read, then writes it back — a classic read-modify-write race with no transaction or optimistic-concurrency check. The code comment even documents an invariant ("Neither reject nor needs-more may ever flip review_state to verified") that this race can violate: whichever `update` lands last wins outright, silently discarding the other decision's effect on `props`, even though both decisions were durably recorded in `review_audit`.
- **Impact**: The audit trail (`review_audit`, meant to be the append-only source of truth for "what happened") ends up inconsistent with `kg_edge.props.review_state` — e.g. two audit rows exist (one confirm, one reject) but the edge shows only the last writer's state, silently undoing a `reject`/`confirm` decision. Since this is explicitly "the ONLY code path allowed to write kg_edge.props.review_state" for a human-review console, a lost update here means an incorrectly-verified (or incorrectly-rejected) financial/political tie ships to end users with no error surfaced anywhere.
- **Fix sketch**: Wrap steps 1–3 in a single transaction (`begin; select ... for update; insert ...; update ...; commit;`) so the read and write are atomic and serialized per edge, or move the whole decision into one SQL statement (`update kg_edge set props = jsonb_set(...) where ... returning props` combined with an `insert ... select` for the audit row) so there's no JS-side read-then-write window.

## 2. Chunked upserts have no transaction — a mid-loop failure leaves partially-applied writes with no rollback
- **Lens**: Bug
- **Severity**: High
- **Category**: transaction-safety
- **File**: lib/db/pglite/internals.ts:102-139 (`upsertMany`); lib/db/pglite/repositories/kg.ts:47-74 (`upsertKgEdges`)
- **Scenario**: A large ingest (the file's own comment cites a 406k-row ballot table split into many ≤500-row chunks) is in progress. Chunk 40 of 200 throws — a transient PGlite WASM error, an out-of-memory condition, or a malformed row that violates a NOT NULL/unique constraint. `upsertMany`/`upsertKgEdges` propagate the exception out of the `for` loop, but chunks 1–39 have already been committed (PGlite auto-commits each statement outside an explicit transaction).
- **Root cause**: Neither helper opens a `begin`/`commit`/`rollback` around the per-chunk loop, so "one upsert call" is not actually atomic — it is N independent auto-committed statements. The function's only success signal is its return value (`written` count) or a thrown exception; there is no way for the caller to know which specific rows landed versus which didn't, and no automatic cleanup.
- **Impact**: A failed re-ingest (e.g. re-running after a source schema hiccup) can leave the corpus in a state that is neither the old snapshot nor the new one — some `id`s updated to new values, others still holding stale data — silently, since callers typically just log-and-retry the whole ingest rather than diffing which chunk failed. Given the natural-key upsert design documented in `ddl.ts` ("re-running an ingest ... updates rows in place"), a half-applied re-run before a crash is exactly the failure mode most likely to go unnoticed until an analyst finds contradictory rows in one table.
- **Fix sketch**: Wrap the full chunk loop of a single logical upsert in one transaction (`await pg.query('begin')` … `commit`/`rollback` on catch), or at minimum have the caller record `written`/failure per ingest run (already has `finishIngestRun`) and treat any thrown error as "ingest_run.status = failed, do not treat existing rows as trustworthy until re-verified."

## 3. `isoDate` normalizes Postgres `date` columns through `toISOString()`, which is timezone-dependent and can shift the calendar day
- **Lens**: Bug
- **Severity**: High
- **Category**: timezone bug / row-mapper coercion
- **File**: lib/db/pglite/internals.ts:64-69
- **Scenario**: `person.birth_date`, `vote_event.voted_on`, `absence.day`, etc. are Postgres `date` (no time-of-day, no timezone). When the driver returns such a value as a JS `Date`, `isoDate` does `v.toISOString().slice(0, 10)`. `toISOString()` always renders in UTC. If the underlying driver constructs the `Date` at local midnight (a common behavior for date-only columns in JS Postgres clients) and the process runs in a timezone east of UTC (e.g. `Europe/Prague`, UTC+1/+2 — exactly where this Czech-data app is likely deployed/dev'd), local midnight is *before* the UTC day boundary, so `toISOString()` renders the *previous* calendar day.
- **Root cause**: The mapper assumes `Date.toISOString()` round-trips a date-only value safely, but that is only true if the `Date` was constructed as UTC midnight; there's no test/assertion pinning which convention the PGlite driver uses, and the function is used for every date field across `person`, `vote_event`, `absence`, `organ`, `mandate`, `membership`.
- **Impact**: Off-by-one-day birth dates, vote dates, or absence days for any deployment/dev environment not running in UTC — a silent, systematic data-integrity bug that would misreport when a roll call happened or when an MP was born, undermining exactly the "provenance and factual accuracy" premise of a civic-transparency tool. Because it fails silently (no exception, just a wrong-but-plausible date), it's unlikely to be caught by casual testing done in a UTC CI environment while showing wrong dates for Prague-based developers/users.
- **Fix sketch**: Extract the date parts with UTC-safe accessors (`getUTCFullYear/getUTCMonth/getUTCDate` if the driver returns UTC-midnight Dates) or, better, request PGlite return `date` columns as raw strings (`::text` cast in the mapper's `select`, or a driver-level type parser) instead of coercing through `Date` at all, then slice the string directly as already done for the non-Date branch.

## 4. `mapMembership` silently coerces any unexpected `kind` value to `"member"`
- **Lens**: Bug
- **Severity**: Medium
- **Category**: silent-failure / row-mapper coercion
- **File**: lib/db/pglite/mappers.ts:129
- **Scenario**: `membership.kind` is stored as free-form `text` (DDL: `kind text not null`, no `check` constraint — contrast with `review_audit.decision`, which *does* have a `check (decision in (...))`). If an ingest writes an unexpected value for `kind` (a psp.cz schema change, a typo in the ingest script, a future third membership kind), `mapMembership` does `str(r.kind) === "function" ? "function" : "member"`.
- **Root cause**: The mapper treats `"member"` as the default/fallback for anything that isn't literally `"function"`, rather than surfacing or flagging unrecognized values. There's no DB-level constraint to catch a bad value at write time, and no logging/throwing at read time either — the two-way narrowing silently absorbs any garbage into the far more common bucket.
- **Impact**: A membership row that was actually meant to encode a distinct kind (or an ingest bug that writes `""`/`null`-as-string/a misspelled kind) gets silently reclassified as a plain member, which changes downstream semantics (e.g. function-holder-only views like committee chairs would miss or wrongly include people) with no error or warning anywhere in the pipeline — a classic "success theater" case where `listMemberships` returns confidently-typed data that quietly misrepresents the source.
- **Fix sketch**: Add a `check (kind in ('member','function'))` constraint at the DDL level (fail fast on ingest) and/or have the mapper throw/log when `r.kind` is neither `"member"` nor `"function"` instead of defaulting, so a schema drift surfaces immediately instead of being absorbed into the majority class.

## 5. Term-scoped queries silently return an empty result set for an unknown/misspelled `termCode` instead of signalling "not found"
- **Lens**: Bug
- **Severity**: Medium
- **Category**: edge-case / silent-failure
- **File**: lib/db/pglite/repositories/votes.ts:63-71 (`listAbsences`); lib/db/pglite/repositories/graph.ts:65-79 (`listMemberships`)
- **Scenario**: A caller passes a `termCode` (organ `abbrev`) that doesn't exist in `organ` — a typo, a term code from a different data vintage, or a term whose organ row hasn't been ingested yet. `listAbsences` builds `where term_psp_id = (select psp_id from organ where abbrev = $1)`; when the subquery matches zero rows it evaluates to SQL `NULL`, and `term_psp_id = NULL` is never true for any row, so the outer query returns zero rows. `listMemberships` has the analogous pattern nested one level deeper (`m.organ_psp_id in (select ... where o.abbrev = $1 or o.parent_psp_id = (select psp_id from organ where abbrev = $1))`).
- **Root cause**: The code conflates two semantically different outcomes — "this term legitimately has zero absences/memberships" and "this term code does not exist in the data at all" — both render as an empty array with no distinguishing signal (no error, no warning, no count check against `organ`).
- **Impact**: A UI page for a mistyped or not-yet-ingested term will render as if everything is fine and simply empty ("no absences recorded", "no members"), rather than surfacing a clear "unknown term" error — exactly the kind of silent failure that's hard to notice in a civic-data tool where an empty section can plausibly mean "clean record" instead of "broken query," and easy to trigger from any request-handling code that forwards a raw path/query param straight through as `termCode`.
- **Fix sketch**: Validate `termCode` against `organ` up front (or have the repository accept/return a "term not found" sentinel distinct from an empty list) before running the scoped query, so callers/UI can distinguish "zero results for a real term" from "the term code itself doesn't resolve."
