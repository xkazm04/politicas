# PGlite Store & Runtime — Combined Bug-Hunt + UI-Perfectionist Scan
> Total: 5

## 1. `store.close()` desyncs the two connection caches, poisoning the next `getStore()`
- **Lens**: Bug
- **Severity**: High
- **Category**: poisoned-state-recovery
- **File**: lib/db/pglite-store.ts:39-44 (also lib/db/store.ts:198-224)
- **Scenario**: Any caller does `const store = await getStore(); ...; await store.close();` and later, in the same process, calls `getStore()` again (e.g. a long-running orchestrator that processes several case-loop batches back to back, a dev-server hot path, or simply a future test file that reuses the pattern already used by `apply-batch.ts`/`kg-compute.ts`/`materialize-tags.ts` — all of which call `getStore()` then `store.close()`). `Store.close()` (pglite-store.ts:39-44) deletes the connection memo keyed by `PGLITE_KEY` on `globalThis` and closes the underlying PGlite handle, but it never touches `lib/db/store.ts`'s own module-level `cached` variable.
- **Root cause**: The bootstrap layer has two independent caches for "is the store open": the `PGLITE_KEY` memo inside `open()` (reset by `close()`) and the `cached: Promise<Store | null>` in `store.ts` (never reset by `close()`, only by `resetStoreCache()` or a rejection). `getStore()`'s very first line is `if (cached !== undefined) return cached;` — after a `close()`, that branch still fires and hands back the *same already-resolved* `Store` object whose methods all close over a `pg` handle that has just been `.close()`d.
- **Impact**: Every method on the returned `Store` (all repository calls) now runs against a closed PGlite connection and rejects, and the failure looks like a random runtime DB error far from the actual cause (`close()` called earlier). Because there is no compile-time or run-time assertion tying `cached` to the connection's real lifecycle, this is a silent trap waiting for the next caller who chains `getStore()` → `close()` → `getStore()` in one process — a pattern the codebase's own scripts (`apply-batch.ts`, `kg-compute.ts`) are one refactor away from doing (e.g. looping over multiple `--which=` batches without spawning a new process per batch).
- **Fix sketch**: Have `Store.close()` also call `resetStoreCache()` (or have `store.ts` own the reset by wrapping the returned store's `close` to clear `cached` before delegating), so the two caches can never point at different lifecycles. Alternatively, make `getStore()`'s cache validity self-checking (store a `closed` flag on the cached `Store` and treat a closed cache entry as `undefined`).

## 2. `storeReady()` never checks `ingest_run.status`, contradicting its own design contract
- **Lens**: Bug
- **Severity**: Medium
- **Category**: readiness-false-positive
- **File**: lib/db/readiness.ts:30-45
- **Scenario**: `docs/architect/decisions/2026-07-26-ingest-readiness-guard.md` states the guard is "(1) A `storeReady()` check consulting `ingest_run` (last run ok + minimum cardinality floor per node kind)". The shipped `storeReady()` only does the second half: it loops over `kinds` and calls `store.listKgNodes({ kind, limit: floor })`, comparing `rows.length` to `CARDINALITY_FLOORS[kind]`. `ingest_run.status` (`ProvenanceRepository.listIngestRuns`) is never read.
- **Root cause**: The cardinality floor is a point-in-time count of the *derived* `kg_node` table, which is populated by a separate offline pass (`kg-compute`) that is not atomic across its node/edge writes (`upsertKgNodes`/`upsertKgEdges` are independent chunked upserts, not one transaction). A prior successful `kg-compute` run can leave `kg_node` sitting comfortably above every floor while the most recent `ingest_run` for the *raw* tables it was derived from is `"failed"` or stuck `"running"` — `storeReady()` has no way to see that and will report `true` regardless.
- **Impact**: The one signal the codebase already has for "did the last write actually succeed" (`ingest_run.status`) is completely disconnected from the readiness gate that four public loaders (`buildLeaderboard`, `getLawData`, `moneyLoader`, `getProfileData`) rely on to decide between real data and a safe fallback. A stale-but-numerically-sufficient `kg_node` snapshot will pass the gate even while the pipeline that's supposed to keep it fresh is actively broken, defeating the "half-ingested graph must not render as truth" goal the decision document sets out to solve for exactly this class of failure.
- **Fix sketch**: Add a "last `ingest_run` for the relevant source(s) is `ok`, not `failed`/stuck `running`" check to `storeReady()` (or a documented companion check called alongside it), as the decision doc originally specified, so a floor pass from stale data can't mask a failing pipeline.

## 3. `KG_READINESS_OFF=1` silently disables the entire readiness gate with zero log trace
- **Lens**: Bug
- **Severity**: High
- **Category**: silent-failure / observability-asymmetry
- **File**: lib/db/readiness.ts:34
- **Scenario**: `storeReady()` opens with `if (process.env.KG_READINESS_OFF === "1") return true;`. The comment warns "never set it in a deployment", but nothing in the code enforces or even flags that it is set. If this env var is ever left on (a copy-pasted `.env` from a test harness, a CI variable that leaks into a preview/prod deploy, an operator debugging locally who forgets to unset it before `npm run build`), every one of the four gated public loaders will serve a half-ingested/empty graph as if it were fully ready — with no console line, no Sentry event, nothing distinguishing this run from a healthy one.
- **Root cause**: The failure path (`storeReady` returning `false`) is loud — it calls `reportLoaderFailure`, which logs and fires a Sentry event (readiness.ts:41-43). The bypass path that suppresses that entire mechanism is given no equivalent instrumentation, so the one state that should be *the most* observable (an intentionally-disabled safety net) is the *only* one that leaves no trace at all.
- **Impact**: Exactly the scenario the whole readiness feature exists to prevent — a partially-ingested graph rendering "real-looking numbers with real citations" (per the architect doc) — becomes reachable in production through a single stray env var, and would be invisible in logs/Sentry/monitoring until a human notices the numbers look wrong.
- **Fix sketch**: When the bypass is active, log a loud, distinctive line (e.g. `console.warn("[readiness] KG_READINESS_OFF=1 — cardinality gate bypassed")`) once per process, and/or have the app refuse to honor the flag outside `NODE_ENV==="test"`, so a leaked env var can't silently disable the gate in a real deployment.

## 4. `pglitePath()` is re-read on every call but the connection it configures is memoized once per process, independent of the path
- **Lens**: Bug
- **Severity**: Medium
- **Category**: stale-config / cache-key-mismatch
- **File**: lib/db/config.ts:31-33 (consumed by lib/db/pglite-store.ts:29-30)
- **Scenario**: `pglitePath()` reads `process.env.PGLITE_PATH` fresh every time it's called, which reads as "the target data dir can be changed per call." But `getPgliteStore()` (pglite-store.ts:29-30) calls the shared `open()` helper, whose connection memo is keyed by a constant global key with no dependency on the path that was used to open it. Once a PGlite connection has been opened in a process, every subsequent call to `pglitePath()` returning a *different* value has no effect — the process keeps talking to the first directory it opened. This is exactly the shape the repo's own PGlite test files rely on staying safe: `readiness.test.ts`, `open-retry.test.ts`, `apply-batch.test.ts`, `leaderboard-loader.test.ts`, and `pglite/repositories/review.test.ts` each set `process.env.PGLITE_PATH` to a distinct temp dir at module load, and the only thing preventing them from silently sharing/corrupting each other's data is Vitest's per-file worker isolation (documented explicitly in `open-retry.test.ts`'s comment) — a test-runner configuration detail, not anything the connection code itself enforces.
- **Root cause**: The bootstrap layer treats "data directory" as immutable-per-process at the connection layer while exposing it as a plain env read at the config layer, with nothing linking the two — the cache has no path-awareness, so a second, differently-configured "open" is a silent no-op that returns the wrong data instead of erring.
- **Impact**: If Vitest's pool configuration ever changes (e.g. `pool: "forks"` with `singleFork`, or a future test consolidation) so two of these PGlite test files execute in the same worker/process, the second file's `PGLITE_PATH` assignment is silently ignored, and its assertions run against the *first* file's temp directory — producing confusing false passes/failures with no error indicating a directory mismatch. The same risk applies to any future script that intends to iterate over several data-dir copies within one long-lived process.
- **Fix sketch**: Key the connection memo by the resolved `pglitePath()` value (a `Map<string, Promise<Pglite>>` instead of a single slot), or have `open()` assert/throw if it's asked to serve a path different from the one already memoized, converting a silent wrong-directory read into a loud, diagnosable error.

## 5. `storeReady()`'s failure report has no throttling, flooding logs/Sentry for the entire duration of any below-floor window
- **Lens**: Bug
- **Severity**: Low
- **Category**: logging-noise / alert-fatigue
- **File**: lib/db/readiness.ts:41-43 (via lib/db/loaderGuard.ts:13-16)
- **Scenario**: `storeReady()` calls `reportLoaderFailure("storeReady", ...)` — an unconditional `console.error` + `Sentry.captureException` — every single time any of the four gated loaders is invoked while the store is below floor. During any expected below-floor window (a fresh deploy before the first ingest completes, a data-dir reset for local dev, or simply the interval between `npm run` ingest passes in a low-traffic environment) every page load that hits `buildLeaderboard`/`getLawData`/`moneyLoader`/`getProfileData` fires a fresh, undeduplicated error report.
- **Root cause**: `reportLoaderFailure` was designed for genuine, presumably-rare degradations (a caught exception at a loader boundary); `storeReady()` reuses it for what is, during initial ingest, an *expected, sustained* condition rather than a one-off failure, with no rate limiting, sampling, or "already reported this session" guard.
- **Impact**: Real, actionable errors reported through the same channel get buried in a flood of expected "not ready yet" noise, and Sentry quota/cost scales with traffic during the entirely normal startup window rather than with actual incident count — undermining the very observability goal `reportLoaderFailure` was introduced for.
- **Fix sketch**: Debounce/dedupe `storeReady()`'s failure report (e.g. log at `warn` level and only fire a Sentry event once per process per below-floor transition, or once per N minutes), so the readiness gate's own instrumentation doesn't drown out unrelated loader failures reported through the same channel.
